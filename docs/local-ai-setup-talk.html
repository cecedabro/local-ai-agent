The model

Qwen3.6-35B-A3B

  • 35B parameters in total, about 3B active per token (mixture of experts)
  • UD-Q4_K_XL GGUF: 22.8 GB, about 5.2 bits per parameter on average
  • A thinking model, post-trained for agentic coding and tool use
  • Multi-token-prediction (MTP) head used as a built-in draft model
  • Clients only ever see the alias coder, so swapping models is a server-side change
Theory · 1

Four words that explain everything after this

Token

The unit of text

A word or a piece of one. ¾ of an English word on average; code uses more. "43 tok/s" means 43 of these per second.

Parameter / weight

One learned number

Training sets billions of them. "The weights" is the file holding all of them: 35B parameters ≈ 22.8 GB at ~5 bits each.

Active parameters

What one token actually uses

Dense model: all of them, every token. Mixture of experts: only the shared parts plus the few experts the router picks.

Context / KV cache

The model's working memory

Every token in the conversation leaves a small summary in memory. It grows with the context and is re-read for every new token.

Theory · 2

Mixture of experts: a big library, a short read

Tokens being generated
One layer: router → experts

■ picked for this token   ■ shared, always used   (illustration; real layers have more experts)

  • Each layer holds many small "expert" networks. A tiny router picks a handful per token.
  • Total parameters ≈ how much the model can know. Active parameters ≈ how much thinking happens per token.
  • Every token picks different experts, so all of them must sit in memory. MoE saves bandwidth, not memory.
  • Folk rule: smarts ≈ a dense model of √(total × active). Here √(35 × 3) ≈ 10B dense. Newer MoEs and "thinking" beat this rule.
Theory · 3

Writing speed is a memory-bandwidth problem

tokens/s ≈ memory bandwidthbytes of active weights

For each new token the model reads every active weight once. The arithmetic is cheap; moving the bytes is not. Halve the bytes (fewer bits, fewer active parameters) or double the bandwidth, and you roughly double the speed.

Theory · 4

Reading a prompt ≠ writing a token

Writing (decode)

One token at a time → bandwidth-bound

  • Only the active experts are read, wherever they live
  • Each weight is read where it sits: VRAM is fast, DDR4 is slow
  • Speed ∝ 1 / (share of active bytes in RAM)
Reading (prefill)

2048 tokens at once → compute + PCIe-bound

  • Across 2048 tokens, nearly every expert gets picked
  • llama.cpp copies the RAM-resident experts to the GPU per batch
  • ~15–18 GB over PCIe 3.0 per batch ≈ 1.3–1.5 s
-ub 512
~280 t/s
-ub 2048
~790 t/s

Agents read far more than they write: every step re-sends files, diffs and test output. That makes prompt reading the number to watch, and it is why bigger batches (one copy serves more tokens) nearly tripled it here.

Theory · 5

Quantisation: rounding billions of numbers

Bits35B modelQuality
16~70 GBoriginal
8~37 GBpractically identical
~5.2 (mine)22.8 GBsmall loss
≤3≤13 GBclearly dumber
  • Block scaling: every ~32 numbers share a scale factor, so 16 levels cover that block's range.
  • "UD" (dynamic): sensitive layers keep more bits; the rest get fewer.
  • Rule of thumb: a bigger model at 4-bit beats a smaller one at 8-bit in the same memory.
Theory · 6

The context window is a memory budget

1 · Training

What the model learned

Past its trained length, quality collapses. Recent Qwen models advertise ~256k, so the model is not my limit.

2 · Memory · my limit

KV cache in VRAM

Grows linearly with tokens and must fit next to the shared layers in 12 GB. So the server runs at 48k.

3 · Speed

Every token looks back

Writing slows as the cache fills; prompt reading grows faster than linearly. Models also get sloppier deep into long contexts.

The harness

A Ralph-style loop: the harness decides "done"

one task =
fresh session
PLAN.md is the only state
  • The model never judges its own work. The harness runs the task's acceptance command plus make check.
  • Fail → git reset, retry with the failure output (3 tries). Still failing → skip; 3 skips in a row → stop.
  • Protected paths (tests, contract, spec, plan) may not change: "fix the code, not the tests".
  • After the tasks: wait for CI, turn failures into fix tasks (max 3 rounds), open a PR. agent-watch does the same for main.
  • Limits: 30 min per attempt, 24 h per run. ntfy pings my phone per task.

Blast radius
  • Own namespace, no service-account token

  • The cluster manifests live in another repo it can't touch
Network
  • Egress: DNS, internet on 80/443, the PC's API + SSH, the waker
  • Private ranges and other pods blocked; ingress closed

  • The devbox SSH key runs a forced command: busy / status / restart only
  • It cannot pause or resume the model; that switch is mine

  • Secrets in OpenBao → External Secrets; never in git
  • Protected paths enforced by the harness, not by the prompt

Lessons

What actually moved the needle

1 · Task size beats model size

One change per task with a concrete acceptance command. "Read only these files" in the task text keeps the context lean.

2 · Smarts beat speed

A model that's right first time at 20 tok/s finishes before one that loops at 60. Retries cost time, CI runs and review effort.

3 · Match every limit

Client context limit = server context. Otherwise the failure looks like "agent made no changes", not "context full".

4 · Make failures loud

A push failure is only logged, so finished work has sat unpushed on the devbox more than once. Every side effect needs a visible check.

5 · Hardware cliffs are sharp

One MoE layer too many on the GPU: 43 → 4 tok/s. Benchmark every flag change.

6 · Humans own the spec

The agent can't edit tests, spec or plan. That one rule prevents most "make the test pass" cheating.

Why it beats old giants

Better data, RL on real edit–test–fix loops, distillation from big models, and thinking tokens.

Why it trails today's frontier

Less stored knowledge (guesses APIs), shallow thinking per token (3B active), 48k context, drifts on long tasks.
